## 新发现的关键问题

### 问题 A：`mvn compile` 必然失败 —— Lombok 注解处理器未执行（**真问题，需要修**）
- 现象：26 个编译错误，全部是"找不到符号"：`@Slf4j` 的 `log`、`@Data` 的 getter/setter、`@AllArgsConstructor` 的构造器
- 根因：**JDK 23 起 javac 默认不再从 classpath 自动发现并运行注解处理器**，而 `maven-compiler-plugin`（Boot 2.3.12 管理的 3.8.1）未配置 `<proc>`
- 验证：加 `-Dmaven.compiler.proc=full` 后 **BUILD SUCCESS**，26 个错误全部消失
- 影响：IDEA 自带注解处理开关（默认开），所以用户日常在 IDEA 里跑没问题；但 `mvn package`、CI、`mvn spring-boot:run` 会挂
- 交接文档"pom 覆盖 lombok.version=1.18.42 即可"的结论**只对了一半**
- 建议修法（待用户确认）：
  ```xml
  <plugin>
    <artifactId>maven-compiler-plugin</artifactId>
    <configuration>
      <proc>full</proc>
      <annotationProcessorPaths>
        <path><groupId>org.projectlombok</groupId>
              <artifactId>lombok</artifactId>
              <version>${lombok.version}</version></path>
      </annotationProcessorPaths>
    </configuration>
  </plugin>
  ```

## 追加（下午）：商户查询缓存第 1 步（基础 Cache-Aside）—— 用户自行实现，实测 12/13

用户自己写完了基础缓存版 `ShopServiceImpl.queryById`，我用 `.workbuddy/tmp/cache_verify.py` 实测。

### 结论：缓存机制本身正确，但有 2 个真缺陷

**已验证正确的部分**（有硬证据）：
- 首次请求 SQL 日志 `Preparing` 0 → 1（未命中确实查了库），缓存 `cache:shop:1` 生成
- 第二次请求 `Preparing` 1 → 1（**新增 0**）→ 命中缓存确实绕过了数据库
- 缓存值类型 string、内容为合法 JSON、id 正确
- 经 nginx 反代 `/api/shop/1` 正常

**缺陷 1：漏设 TTL（真 bug）**
- 代码：`stringRedisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(shop))` —— 无第三/四参数
- 实测：`TTL = -1`（永不过期）
- 后果：`updateShop` 改库后缓存永不失效，前台永远看到旧数据；TTL 的兜底作用完全丧失
- 修法：补 `CACHE_SHOP_TTL, TimeUnit.MINUTES`

**缺陷 2：`IShopService.queryById` 返回 `Object`，导致 `Result.fail` 被 `Result.ok` 包了一层（真 bug，影响前端）**
- 现状：接口签名 `Object queryById(Long id)`；实现里混返 `Shop`（命中/写回后）与 `Result.fail("店铺不存在")`（未命中库）
- Controller：`return Result.ok(shopService.queryById(id));`
- 实测响应：`{"success":true,"data":{"success":false,"errorMsg":"店铺不存在"}}`
- **前端证据**：`nginx-1.18.0/html/hmdp/js/common.js:18-23` 的 axios 响应拦截器
  ```js
  if (!response.data.success) { return Promise.reject(response.data.errorMsg) }
  return response.data;
  ```
  只看**顶层** `success`。顶层是 `true` → 不 reject → 把 `{success:false,errorMsg:...}` 当店铺对象交给页面渲染 → 页面空白而非提示"店铺不存在"
- 推荐修法：签名改成 `Result queryById(Long id)`，失败分支返回 `Result.fail(...)`，Controller 直接 `return shopService.queryById(id);`
  - 理由：与课程一致；且下一节「缓存穿透」必须返回 `Result.fail`，此签名可复用
- 备选修法：签名改成 `Shop` + 失败抛异常。但项目现有的 `WebExceptionAdvice` 对**所有** RuntimeException 一律返回 `Result.fail("服务器异常")`，会把"店铺不存在"吞成"服务器异常"并打错误堆栈 → 需自建业务异常才可行，成本更高

### 关键工具
- `.workbuddy/tmp/cache_verify.py` —— 商户缓存验证脚本（自动挑真实 id、清缓存、校验 TTL/类型/JSON、用 SQL 日志计数证明命中、检查空值缓存行为、走 nginx）
- `.workbuddy/tmp/HutoolJsonProbe.java` —— 实测 **Hutool 5.7.17 的 `JSONUtil` 对 `LocalDateTime` 可无损往返**（序列化为毫秒时间戳，反序列化还原一致）；而裸 `new ObjectMapper()` 会抛 `InvalidDefinitionException`

### 其它现场信息
- `updateShop` / `saveShop` 仍直接改库、不同步缓存 —— 这是课程**故意留到缓存章节末尾**才讲的一致性话题，当前不算缺陷
- 空值未缓存（`cache:shop:999999` 不存在）→ 正是下一节「缓存穿透」的入口

## 追加（16:26）：商铺类型缓存（`/shop-type/list`）教学设计

用户主动要求先不进入缓存穿透，改为完善商铺类型缓存。

### 现场代码状态
- `ShopTypeController.queryTypeList()`（**注意方法名不是 `queryShopById`**，路由 `GET /shop-type/list`，在登录白名单内）
  目前直接 `typeService.query().orderByAsc("sort").list()` 打库
- `IShopTypeService` / `ShopTypeServiceImpl` 均为空壳
- `RedisConstants` **没有**商铺类型的 key 常量 → 需新增
- `ShopType` 实体：`id / name / icon / sort` + `createTime / updateTime`（后两个标了 **Jackson 的** `@JsonIgnore`），类上有 `@Accessors(chain = true)`

### 实测（用 `target/classes` 里真实的 ShopType 类，cp = target/classes + hutool-all-5.7.17 + jackson-annotations-2.11.4）
```bash
"E:/java/jdk25/bin/java.exe" -cp "target/classes;$H;$J" .workbuddy/tmp/ShopTypeJsonProbe.java
```
脚本：`.workbuddy/tmp/ShopTypeJsonProbe.java`

| 观察点 | 结论 |
|---|---|
| `@Accessors(chain = true)` 链式 setter → Hutool `toList`/`toBean` 能否赋值 | ✅ **能**，所有字段正常（提前排除了"静默 null"隐患） |
| `@JsonIgnore`（Jackson 注解）对 Hutool 是否生效 | ❌ **不生效**，缓存 JSON 里**含** `createTime`/`updateTime`（毫秒时间戳） |
| 顺序是否保持 | ✅ 保持 |
| 3 个元素序列化长度 | 322 字符 |

→ 缓存里多两个字段**不影响正确性**（Jackson 出参时会再过滤掉），只是多占空间。

### 给出的设计要点（供后续复习）
1. **与商户缓存的本质区别**：`/shop-type/list` 无参数、只有一个固定 key、返回集合；
   "查不到"对列表而言是**空数组而非错误** → 所以 service 返回 `List<ShopType>`，
   Controller 保留 `Result.ok(...)` 即可，**不需要**像 shop 那样把返回值改成 `Result`
2. 新增常量建议：`CACHE_SHOP_TYPE_KEY = "cache:shopType"`（无 id 后缀故**不带尾冒号**）、`CACHE_SHOP_TYPE_TTL = 30L`
3. **取舍：整个 List 序列化成一个 String（`opsForValue`）vs Redis List 类型（`opsForList`）**
   → 选前者：字典数据总量小、前端要全量拿，分页无意义；`opsForList` 更新时须先删再推、无法原子替换
4. 空列表先直接返回、不缓存（与 shop 一致），留待穿透章节统一处理
5. 提醒**必须设 TTL**（承接缺陷 1）

### 两个关键发现（与用户预期可能不符）

   - `E:\Git\cmd\git.exe` → 2.54.0，`credential.helper=manager`（GCM）

### 结论与建议

3. **报错 `Failed to connect to github.com port 443 after 21095 ms: Could not connect to server`**
   → 根因是**代理**：本机系统代理已开（`127.0.0.1:7897`，进程 `com.vortex.helper.exe`），但 **git/IDEA 默认都不读系统代理**
   → 决定性对比实验：
      | 条件 | 结果 |
      |---|---|
      | 不走代理 | 42.1s 后 `Recv failure: Connection was reset` |
      | 走 127.0.0.1:7897 | **2.8s 成功** |
   → 修复：`git config --global http.proxy/https.proxy http://127.0.0.1:7897` + IDEA HTTP Proxy 手动配 127.0.0.1:7897
   → DNS 正常（20.205.243.166），排除 DNS 问题
